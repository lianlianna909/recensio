## 1. ADR-LIC-001：项目许可证 = Apache License 2.0

**状态**：ACCEPTED（记录）/ 执行待批

### 决定

本项目采用 **Apache License, Version 2.0**（SPDX：`Apache-2.0`）。

### 理由

| 理由 | 说明 |
|---|---|
| 明确专利授权 | §3 给予贡献者与下游使用者显式专利许可，避免「只给版权不给专利」的隐含风险 |
| 专利诉讼终止条款 | §3 规定发起专利诉讼即终止授权，对机构采用方是保护 |
| 适合长期开放维护与机构采用 | 高校、研究院、企业法务对 Apache-2.0 的接受度高于 MIT（因专利条款），低于 AGPL（无传染） |
| 允许商业使用、修改、再分发 | 无 copyleft，不限制闭源集成与商业分发 |

### 实施要求（记录，未执行）

1. 根目录建立完整 `LICENSE` 文件，内容为 Apache-2.0 **官方原文，逐字不改**（来源 `https://www.apache.org/licenses/LICENSE-2.0.txt`，创建时取原文，不得改写、不得节选）。
2. 建立项目 `NOTICE` 文件。
3. 自有源代码统一使用 `SPDX-License-Identifier: Apache-2.0` 标识。
4. 对适合的源码文件添加统一版权与许可证 Header。
5. 保留第三方源文件原有许可证与版权声明。
6. **不将** Apache-2.0 Header 添加到第三方代码。

### 必须区分的两件事（用户明确要求）

| 类别 | 内容 | 性质 |
|---|---|---|
| **Apache-2.0 的法律要求** | 分发时须附带许可证副本；修改过的文件须显著标注；若分发物含 `NOTICE`，须一并传递且不得改写其归属声明（§4） | 法律义务，不做即违约 |
| **本项目主动采用的合规管理规范** | 每个文件加 SPDX 标识与版权 Header；维护 `THIRD-PARTY.md`；CI 许可证检查；SBOM | 工程规范，Apache-2.0 **不强制**；目的是可审计、可交接、降低误引入风险 |

> 这条区分很重要：**Apache-2.0 并不要求每个源文件带 Header**。要求 3、4 是项目自律，不是法律义务。反过来，要求 1、2、5 是法律义务，不能省。

### NOTICE 的准确性约束

- `NOTICE` 只写**真实存在**的归属信息。
- 当前仓库**无任何第三方依赖**（见 §4 实测），因此 `NOTICE` 初期只含项目自身一行，**不得虚构任何第三方名称、商标或贡献者**。
- 后续引入带 `NOTICE` 的第三方组件时，只能**逐字追加**其原始 NOTICE 片段，并注明来源与版本。

## 2. ADR-LIC-002：贡献者协议 = DCO 1.1

**状态**：ACCEPTED（记录）/ 执行待批

### 决定

采用 **Developer Certificate of Origin 1.1**（DCO）。**暂不采用 CLA。**

### 要求（记录，未执行）

1. 建立 `DCO.md`，包含 **DCO 1.1 完整原文**（来源 `https://developercertificate.org/`，逐字，不节选、不改写）。
2. `CONTRIBUTING.md` 明确要求每个提交包含 `Signed-off-by` 行。
3. 提交使用 `git commit -s`。
4. PR 检查 DCO 签署状态。
5. 贡献者必须确认自己有权提交该贡献。
6. 涉及雇主或机构所有的知识产权时，要求额外授权确认。
7. **不得**将 DCO 描述为版权转让或双重许可授权。

### DCO 的法律性质（必须写清，避免误导贡献者）

| 常见误解 | 事实 |
|---|---|
| 「签了 DCO 就是把版权转给项目」 | **错**。DCO 是贡献者的**声明与保证**，不是版权转让。贡献者保留版权 |
| 「签了 DCO 等于同意双重许可」 | **错**。DCO 不含任何再许可授权。项目若日后要做闭源双许可，**现有 DCO 贡献无法直接复用** |
| 「DCO 是合同」 | 严格说是开发者对项目的声明（certification），不是双方签署的合同 |

### 未来变更触发条件

若决定提供闭源商业双许可版本，**必须重新评估 CLA 与贡献授权体系**——届时需要能覆盖历史贡献的授权链，而 DCO 提供不了。这是选择 DCO 的主要代价，已知并接受。

### 对既有提交的影响

现有 8 个提交（`e0e9af6` … `1467136`）**均无 `Signed-off-by`**，全部由本会话的自动化流程产生。
- **不改写历史**（用户明确禁止）。
- 处理方式：在 `CONTRIBUTING.md` 中记录「`1467136` 之前的提交为项目初始化提交，DCO 要求自本 ADR 生效后的第一个提交起适用」。
- 该说明**只作事实记录**，不构成对这些提交的追认或豁免声明。

## 3. ADR-LIC-003：第三方依赖治理

**状态**：ACCEPTED（记录）/ Phase 1 起强制执行

### 决定

建立 `THIRD-PARTY.md`，**每个新依赖必须登记**，未登记不得引入。

### 登记字段（缺一不可）

| 字段 | 说明 |
|---|---|
| 名称 | 包名 / 组件名 |
| 精确版本 | 锁定版本，不接受版本区间 |
| 来源仓库 | 官方仓库 URL |
| 许可证 SPDX ID | 如 `MIT` / `Apache-2.0` / `BSD-3-Clause` |
| 用途 | 在本项目中做什么 |
| 分类 | Runtime / Development / Test |
| 是否随发行包分发 | 是 / 否 |
| 是否包含 NOTICE | 是 / 否；是则须登记其内容位置 |
| 许可证审查结论 | 允许 / 需人工批准 / 禁止 + 依据 |

### 规则

1. **未知许可证禁止引入。**
2. **GPL / AGPL 默认禁止**，特殊情况必须人工批准并书面记录理由。
3. **MIT、BSD、ISC、Apache-2.0 原则上允许**，但仍需检查具体文件与附加条款（例如 BSD-4-Clause 的广告条款、Apache-2.0 的 NOTICE、MIT 的变体措辞）。
4. **MPL、LGPL 等逐项审查**（弱 copyleft，取决于链接方式与修改程度）。
5. **字体、图标、模型、模板、示例数据、图片素材**同样纳入审查——这类资产常被误认为「不算依赖」。
6. 检查**直接依赖与实际分发到的传递依赖**。
7. 每次依赖变更同步更新 `THIRD-PARTY.md`。
8. 后续加入 CI 许可证检查与 SBOM 生成（方案见 §6）。

### 与本项目既有结论的衔接

| 既有结论 | 与 ADR-LIC-003 的关系 |
|---|---|
| 不 Fork 任何项目（D-09） | 无 Fork ⇒ 无「把第三方源码纳入本仓库」的情形，规则 5 之外的第三方源码引入为零 |
| TeXlyre / Oleafly AGPL → Reference-only | 不引入代码，仅阅读文档，不产生依赖登记义务 |
| Pandoc GPL-2.0-or-later → 进程级调用 | **已定（P6）：要求用户自行安装。** 引擎启动时探测系统 `pandoc`，缺失则提示安装指引，**不随产品分发 pandoc 二进制**。因此本项目不承担 Pandoc 的 GPL 分发义务，仅需在 `THIRD-PARTY.md` 登记「开发/运行期外部依赖，不随发行包分发」。`PANDOC_BOUNDARY.md` 中「随产品分发」与「SaaS」两种情形保留为文档记录，不适用 |

## 6. 许可证检查方案

分三阶段，随项目成熟度递进。**Phase 1 开工只需阶段一。**

### 阶段一：人工登记 + Header 校验（Phase 1）

| 项 | 方案 | 说明 |
|---|---|---|
| 依赖登记 | `THIRD-PARTY.md` 手工维护 | 依赖数量在 Phase 1 极少（预期 <10），手工可控 |
| Header 校验 | FSFE `reuse` 工具的 `reuse lint` | 校验每个文件是否有 SPDX 标识与版权信息；**引入前需实测其对本仓库的判定** |
| 引入审批 | PR 模板勾选项 + 指定审批人 | 「本 PR 是否新增依赖？是则附 THIRD-PARTY.md 变更」 |

### 阶段二：自动化扫描（首个外部依赖落地时）

| 生态 | 候选工具 | 状态 |
|---|---|---|
| Python | `pip-licenses`、`licensecheck` | 待实测 |
| Node | `license-checker-rseidelsohn` | 待实测 |
| 通用 | `reuse`（SPDX 合规） | 待实测 |
| SBOM | CycloneDX（`cyclonedx-py` 等） | 待实测 |

> 上表工具名均为候选，**未在本机验证**。Phase 1 引入前须逐个实测其对当前技术栈的支持度，不通过则不采用。

### 阶段三：CI 门禁（Phase 2 起）

流水线在每次 PR 上执行：

```
1. reuse lint                → SPDX header 缺失即失败
2. 依赖许可证扫描            → 检出 GPL/AGPL/未知即失败
3. THIRD-PARTY.md 一致性检查 → 依赖清单与登记表不一致即失败
4. SBOM 生成并归档
```

**放行规则**

| 许可证 | 处理 |
|---|---|
| MIT / BSD-2 / BSD-3 / ISC / Apache-2.0 | 自动通过（仍需检查附加条款） |
| MPL-2.0 / LGPL-2.1 / LGPL-3.0 / EPL-2.0 / CDDL | 警告 + 需人工批准 |
| GPL-2.0 / GPL-3.0 / AGPL-3.0 | **失败**，需书面例外 |
| 未知 / 无许可证 / 自定义条款 | **失败** |

**例外机制**：`compliance/exceptions.yaml`，每条含「包名 + 版本 + 理由 + 批准人 + 批准日期 + 复审日期」。无此记录一律视为未批准。

### 背景

项目对外名称为 `Recensio`，但仓库目录仍为 `ScientificWritingProject`。为避免发布时被迫改名，需区分「可改」与「不可改」两类标识。

### 规则

**所有持久标识符一律使用 `recensio`，不使用 `ScientificWritingProject`。**

| 标识符 | 是否可事后更改 | 处置 |
|---|---|---|
| 仓库目录名 | 可（本地路径） | 暂不改 |
| GitHub 仓库名 | 可（GitHub 自动重定向旧 URL） | 发布前改 |
| PyPI 发行名 | **不可**（发布后不可复用同名） | **必须用 `recensio`** |
| npm 包名 | **不可**（发布后不可复用同名） | **必须用 `recensio`** |
| Python 导入包名 | 成本极高（所有 import 路径） | **必须用 `recensio`** |
| CLI 可执行文件名 | 高（用户脚本、文档、PATH） | **必须用 `recensio`** |
| Obsidian 插件 ID | **不可**（发布后改 ID 等于换插件，用户需重装） | **必须用 `recensio`** |
| 配置文件 / 环境变量前缀 | 高（用户配置会失效） | **必须用 `recensio` / `RECENSIO_`** |
| Vault 目录名 | 可（但会影响用户既有数据） | 与名称无关，按架构 §3 |

### 结论

仓库目录名保留 `ScientificWritingProject` 不影响发布——因为它不出现在任何对外产物中。真正会锁死的是包名、CLI 名、插件 ID 与配置前缀，这四项从 Phase 1 第一行代码起就必须是 `recensio`。

**发布前必做**：GitHub 仓库改名为 `recensio`（旧链接自动重定向）。
